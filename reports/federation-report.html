Data Platform and Tools Federation

Reference Implementation — Proving federated governance across five live platforms

The problem. Large organizations do not choose one data platform. They inherit several — Redshift for warehousing, S3 and Glue for the data lake, Snowflake for specific business units, Databricks for data science. Each platform works well in isolation. The problems appear at the boundaries: no unified catalog, no cross-platform query capability, no single view of who has access to what, and no unified audit trail. Every cross-platform join becomes an ETL project. Regulatory audits require collating evidence from multiple consoles by hand.

The deeper issue. The estate is not static. New platforms, new engines, and new use cases arrive continuously. Without a decoupling layer, each addition multiplies the integration burden. The cost of integration grows with the number of platforms, not the value being extracted from them.

The approach. We built a federation layer using three open-source components — Gravitino (metadata), Ranger (policy), and Trino (query) — deployed above five live platforms (AWS Redshift, S3/Iceberg, Snowflake, Databricks Unity Catalog, AWS Glue). The layer replaces nothing; every platform keeps its own security controls unchanged. We validated the architecture with an 88-test suite organized into four scenarios that prove capability, trust, safety, and identity differentiation.

Architecture: Three Planes

Solving the boundary problems requires three interdependent planes. Remove any one and the architecture collapses: a catalog without policy is ungoverned; policy without a query engine is unenforceable; a query engine without a catalog requires per-platform configuration that does not scale.

PlaneComponentQuestionWhat it provides
Metadata Gravitino What exists? Single namespace across all platforms — datasets, models, and schemas discoverable in one catalog regardless of where they live
Policy Ranger Who can touch it? Extracts and normalizes entitlements from every platform into one queryable policy store; enforces them at the Trino layer; provides unified audit trail
Query Trino How do I get it? Cross-platform SQL — any combination of sources in one query. Built-in Ranger plugin provides enforcement at the federation layer
Safety property: Every federated query passes two independent checks. At lookup time, Ranger checks extracted entitlements (which can be stale). At run time, the source platform enforces its own controls (always current). A stale Ranger mirror can block a legitimate user until sync, but it cannot grant access the platform has revoked. The sync gap creates noise, not risk.

Scenario 1: The Report

Can we federate?
Question: Can an analyst discover, query, and analyze data across five platforms without knowing where it lives?

An analyst sits down with one identity, discovers data from five platforms through a single Gravitino catalog, and builds a counterparty exposure report. They sample each source — Redshift (hot), S3/Parquet (warm), Iceberg (cold), Snowflake (reference), Databricks (risk signals) — through one Trino session. Snowflake Cortex generates cross-platform SQL from the metadata context, and the analyst executes it. Spark independently confirms the Iceberg data matches Trino's count.

What it proves:
Five-format federation works from a single SQL session. The unified catalog eliminates platform-specific discovery. LLM-powered analysis chains metadata → SQL generation → execution without manual schema lookup.

Scenario 2: The Audit

What it proves:
Federated results are mathematically accurate, not approximate. Every access is auditable. Every policy has provenance. The entitlement view is unified and queryable, not scattered across platform consoles.

Scenario 3: The Failure Modes

What if it breaks?
Question: When the federation layer's view of permissions is stale, does the system fail open or fail closed?

We formalized the safety property as a 16-combination truth table: four Ranger states × four platform states. Every combination produces a safe outcome. A stale Ranger allow is blocked by the platform; a stale Ranger deny blocks until sync. We then contrasted governed vs. ungoverned paths — same data, two routes, different audit coverage. We proved the ABAC-to-RBAC translation pipeline labels every fidelity loss. And we added Databricks as the fifth platform without changing a single existing query or policy.

What it proves:
The sync gap creates noise, not risk — the safety property is computed, not claimed. Lossy translations are documented, not hidden. Adding a platform is an event, not a project.

Scenario 4: The Identities

Does it actually differentiate?
Question: Do policies actually enforce different behavior for different users, or are they just configuration artifacts?

Same SQL. Five users. Five different views. alice (analyst) sees masked PII — token_id is hashed. bob (risk investigator) sees the raw value — group exception. frank (external auditor) gets Access Denied on the risk_signals table entirely. Every access is captured in per-identity audit events in Solr. Row filter policies differentiate groups, though runtime enforcement awaits a Ranger plugin update.

What it proves:
Governance is active, not illusory. Same query, different results based on identity. Column masking, table denial, and per-identity audit all work through group-based policies.

Conclusion: Three Planes, Three Access Patterns

The four scenarios prove the thesis from different angles: federation works (S1), results are trustworthy (S2), the system fails safely (S3), and governance differentiates by identity (S4). The conclusion tests confirm the architecture is decouplable and extensible.

Three Access Patterns

Every data interaction falls into one of three patterns, each independently governed:

PatternWhatEnforcementBackstop
Discover See metadata (schemas, tables, columns, tags) Gravitino visibility + platform catalog ACLs Platform metadata access controls
Query Execute SQL, get governed results Ranger at Trino; source RBAC for direct connections Platform RBAC (Redshift, Snowflake, UC)
Access Obtain scoped credentials to storage Platform validates entitlements, vends scoped temporary credentials Credential vending = platform-native enforcement

Decoupled Cost

Adding Databricks as the fifth platform required one Trino catalog file, one Gravitino registration, and one Ranger extractor. No existing queries changed. No existing policies changed. The fifth platform cost less to integrate than the second. Adding a platform is an event, not a project.
